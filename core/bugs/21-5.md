# PRD — Manooch Minimum Order Value on Storefront Counters (compact)

You are a senior engineer on **Manooch**, a multi-store SaaS e-commerce platform ("Powered by Manooch"). I need a plan to fix **minimum order value** handling in the storefront **counter components** (on the PDP and on product cards). Please analyze root cause, give the correct behavior, and provide a concrete fix plan (+ illustrative code) to implement and test end-to-end.

**Context:** A product can have a **minimum order value** configured. This applies to a **unit** (when unit pricing is on) or to the **product itself** (when unit pricing is disabled). Today, the **minimum order value is not working** in the counter components on the PDP or on the product card on the storefront.

**Repository branch to work on:** `fix-minimum-order-storefront` — push the fix to this branch.

---

## Behavior wanted

1. **First interaction = minimum order.**
   - When the user first clicks the **plus (+) button** (or it is the **default selected** value), the counter should add the **minimum order quantity** of that variant to the cart/bucket.
   - Example: I set minimum order `4` for a product → the first time the user adds it, they should see **4** of the variant added.
   - Example: a pencil with **minimum order 2** → clicking the counter adds **2** of it.

2. **Increment base = +1.**
   - After the initial minimum-order amount is in place, subsequent **+ clicks increment by +1**.

3. **Minus behavior.**
   - When the counter is at the **minimum order value** and the user clicks **minus (−)**, the item should be **removed from the cart entirely**.

---

## Deliverables: root cause • correct behavior • recommended fix • edge cases.
**Edge cases:** minimum order applies to a unit (unit pricing on) vs the product itself (unit pricing off); product card vs PDP counter; default-selected value = minimum order on first render; increment +1 after the minimum; minus at the minimum removes the item from cart; making sure the minimum is not bypassed by rapid +/- clicks.

## Issue 2 — Seller can't re-register a store after the super admin deletes it

**Context:** As a **super admin** I manage stores. In the **store config → danger zone**, I can **completely delete a store**.

**The bug:** After I **completely delete a store** from the danger zone, the **seller should be able to create a new store with the same number** — but instead, during authentication, they get an error saying **"you already have a store with this number"** (the `ALREADY_HAS_STORE` / single-store-per-number check still sees the old store as existing).

**Expected:** When a store is **fully/deleted removed** via the danger zone, the phone number is **freed up**, so the seller can register a **new store with that same number** without the "already has a store" error blocking them.

**Question:** Why does the "already has a store" check still trigger after a store is deleted from the danger zone? Is the store only soft-deleted / not truly removed, so the number is still considered owned? What should be cleaned up (hard delete or flag) so the number becomes reusable for a new store?

## Deliverables for Issue 2: root cause • correct behavior • recommended fix • edge cases.
**Edge cases:** danger-zone deletion must truly free the number (not just soft-delete); any related data (sellers, store records, entitlements) cleaned up or handled so re-registration with the same number works; ensuring this doesn't affect the earlier min-order fix or the `fix-minimum-order-storefront` branch work.
