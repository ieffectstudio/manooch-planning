# Manooch — UI/UX Alignment & Fix Prompt
**Scope:** Visitor plugin · Storefront plugin · Admin panel
**Type:** Design & behavior specification only — do NOT include coding logic, implementation details, or code snippets. Describe *what* must change and *how it must look and behave*, not *how to code it*.

---

## Context

The Manooch project consists of multiple surfaces: an **Admin panel**, a **Visitor panel (plugin)**, and a **Storefront (plugin + Dashboard storefront)**. The goal of this task set is to make the Visitor panel visually and behaviorally consistent with the Admin panel and the other plugins, align several Storefront elements with the Visitor panel where specified, fix one admin layout issue, fix one config activation bug, and simplify the Storefront orders area.

Two reference screenshots are attached to this prompt:
- 📎 `add-to-card.png` — reference for the product card design (Dashboard storefront `productCard`).
- 📎 `order-filter-button.png` — reference for the admin orders page filter-button placement.

---

## 1. Visitor Panel — Header (AdminTopBar + Switch Account)

**Current behavior**
- The Visitor panel uses its own custom header, which does not match the Admin panel header in structure, spacing, or behavior.

**Required change**
1.1. Replace the Visitor panel's existing header entirely with the **AdminTopBar** component — the same top bar used across the Admin panel — so the Visitor panel is visually and structurally identical at the top of the page.
1.2. Add a **"Switch Account"** button inside that top bar.
1.3. **Position:** the "Switch Account" button must be rendered **immediately before the "Back" button** in the reading/flow order of the layout (i.e., on the start side of the Back button, directly adjacent to it, respecting the active text direction of the UI).
1.4. The "Switch Account" button must inherit the **exact same button styling system** used in the AdminTopBar (size, padding, typography, border-radius, icon usage, hover/active/disabled states) so it looks native to the bar — not like a foreign element.
1.5. All existing AdminTopBar behaviors (titles, navigation context, responsive collapse behavior) must remain intact. The Back button keeps its current behavior; only the new button is added before it.

**Acceptance criteria**
- Visitor header is pixel-consistent with the Admin panel's top bar.
- "Switch Account" appears directly before "Back" and is visually indistinguishable in quality/style from the other top-bar actions.
- No layout shift or overflow occurs on the smallest supported viewport width.

## 2. Visitor Panel — Global Styling (Match Admin Panel / Other Plugins)

**Current behavior**
- The Visitor panel's visual language (colors, and other visual tokens) diverges from the Admin panel and from the other plugins hosted in the panel.

**Required change**
2.1. Re-skin the **entire Visitor panel** to follow the **Admin panel design system**, the same way every other plugin in the panel already does. This includes, at minimum:
   - **Color palette:** background colors, surface/card colors, border colors, text colors (primary/secondary/muted), and semantic colors (success, warning, error, info) must come from the admin theme tokens — no visitor-specific hardcoded colors.
   - **Primary/accent color:** match the admin panel's primary color across buttons, links, active states, tabs, badges, and focus rings.
   - **Typography:** font family, sizes, weights, and line-heights identical to the admin panel's type scale.
   - **Spacing & layout:** page paddings, section gaps, card padding, and grid gutters consistent with the other plugins.
   - **Component styling:** buttons, inputs, selects, toggles, tables, modals/dialogs, dropdowns, tooltips, and empty states must all reuse the admin panel's component styles and interaction states (hover, focus, active, disabled, loading).
   - **Elevation & shape:** same border-radius values, shadows, and dividers as the admin panel.
   - **Iconography:** same icon set, sizes, and stroke/fill treatment as the admin.
2.2. Dark/light mode (if the admin panel supports it) must work in the Visitor panel exactly as it does elsewhere.
2.3. The result must be that a user **cannot tell** they have switched from one plugin to the Visitor plugin — seamless visual continuity.

**Acceptance criteria**
- Side-by-side comparison of the Visitor panel and any other plugin shows the same palette, type, spacing, and component styles.
- No visitor-specific color values or one-off styles remain; everything derives from the shared admin theme.
- Interactive states (hover/focus/active/disabled) behave identically to the admin equivalents.

## 3. Visitor Panel — Card Style (Match Dashboard Storefront productCard)
📎 Reference screenshot: `add-to-card.png`

**Current behavior**
- Cards in the Visitor panel use a different layout and visual treatment from the product cards used in the Dashboard storefront.

**Required change**
3.1. Restyle the Visitor panel cards so they are **visually identical in structure and styling to the `productCard` used in the Dashboard storefront**, as shown in the attached screenshot. This includes:
   - **Layout & composition:** same arrangement of image/media area, title, description/secondary text, price/metadata row, and action area.
   - **Media:** same image aspect ratio, object fit behavior, corner rounding, and placeholder state for missing images.
   - **Card container:** same background, border, corner radius, shadow/elevation, and hover elevation/highlight effect.
   - **Content typography:** same hierarchy, sizes, weights, truncation/line-clamping behavior (e.g., max lines for title and description with ellipsis).
   - **Action area:** buttons/badges placed and styled as in the storefront productCard.
   - **Grid behavior:** cards must size and wrap in the Visitor panel grid the same way productCards do in the storefront (equal height rows, consistent gaps, responsive column behavior).
3.2. While the **structure and component design** must mirror the storefront productCard, the **colors** still follow the admin panel theme per Item 2 (structure from storefront, palette from admin).

**Acceptance criteria**
- A Visitor card placed next to a Dashboard storefront productCard matches in layout, proportions, media treatment, and action placement (screenshot-reference accurate).
- Hover/press states and equal-height grid behavior match the storefront card behavior.

## 4. Storefront — "Add to Cart" CTA (Visitor Interaction, Storefront Primary Color)

**Current behavior**
- The Storefront's add-to-cart call-to-action (CTA) looks/behaves differently from the Visitor panel's add-to-card CTA.

**Required change**
4.1. Adopt the **Visitor panel's "Add to Card" CTA design and interaction pattern** for the Storefront's add-to-cart CTA — same button geometry (size, padding, shape, icon + label arrangement), same states (default, hover, pressed, loading, added/success feedback, disabled), and same micro-interactions/feedback animation.
4.2. **Color exception:** although the style comes from the Visitor panel, the CTA's color must use the **Storefront's primary color** (the storefront theme's primary token) — including its hover/active/pressed shades derived from that primary color. It must **not** inherit the visitor/admin primary color.
4.3. This applies everywhere the add-to-cart CTA appears in the Storefront (product cards, product detail view, and any quick-add surfaces) — one consistent CTA treatment across all of them.
4.4. Added-to-cart feedback (e.g., success state, counter bump, toast/badge update) must follow the Visitor CTA's feedback pattern, themed with the storefront primary color.

**Acceptance criteria**
- The Storefront add-to-cart CTA is visually and behaviorally the same as the Visitor add-to-card CTA, except the color is unmistakably the Storefront primary color.
- All states (hover/loading/success/disabled) exist and are consistent across every surface where the CTA appears.

## 5. Admin Panel — Orders Page: Filter Button Repositioning
📎 Reference screenshot: `order-filter-button.png`

**Current behavior**
- On the Admin orders page, the **filter button** is currently positioned away from where users expect it (see screenshot), which breaks the visual grouping of the toolbar controls.

**Required change**
5.1. **Move the filter button** so that it sits **below the search input**, positioned **in front of / adjacent to the orders counter** (the element showing the number of orders), exactly as indicated in the attached screenshot.
5.2. The filter button and the counter must be visually grouped on the same row: aligned on the same baseline, with the same control height, and with spacing consistent with the admin design system's toolbar gap.
5.3. The search input remains on its own row above; the new row directly beneath contains: filter button + counter (in the order shown in the screenshot, respecting UI direction).
5.4. No functionality change: the filter button opens the same filter UI as before; only its placement and alignment change.

**Acceptance criteria**
- Layout matches the screenshot: search on top; filter button below it, in front of the counter, one aligned row.
- Row alignment, heights, and gaps match admin toolbar standards.
- Responsive behavior holds with no overlap, truncation, or overflow on the narrowest supported admin viewport.

## 6. Personalize Config — Conditional Payment Not Activating (Bug)

**Current behavior**
- In the **Personalize configuration**, when **"Conditional Payment"** is checked/enabled, the setting **does not actually take effect** — the feature stays inactive even though the UI shows it as enabled.

**Required change**
6.1. Enabling the Conditional Payment option in the personalize config must **genuinely activate the feature** — the checked state must persist, be saved, and drive the actual runtime behavior that conditional payment is supposed to control.
6.2. The UI state must always reflect the **true** state of the feature:
   - If the user checks it and saves, the feature must be on, and on revisit the checkbox must show as checked.
   - If the user unchecks it, the feature must be off, with the same persistence guarantee.
6.3. Any dependent UI or behavior that should appear when conditional payment is active (per its original specification) must appear/function once it is enabled — and disappear when disabled.
6.4. Add clear failure feedback: if activation cannot be saved/applied for any reason, the user must see an error state/message instead of a silently ineffective checked box.

**Acceptance criteria**
- Checking + saving Conditional Payment results in the feature being verifiably active (its dependent behavior works).
- State persists across page reloads and sessions.
- Unchecking fully disables the feature.
- Silent failure is impossible: the displayed state always equals the real state, or an explicit error is shown.

## 7. Storefront — Orders Page Restyle + Remove Reorder Page

**Current behavior**
- The Storefront **Orders** page does not follow the same page design as the Storefront **Notifications** page — differences include the background image treatment (sizing/fitting) and the empty-state presentation.
- A separate **Reorder** page exists in the Storefront and is no longer wanted.

**Required change**

**7A. Orders page — match the Notifications page style**
7.1. Restyle the Storefront Orders page to follow the **Notifications page design**, specifically:
   - **Background image:** use the same background image handling as the Notifications page — same sizing/fitting (cover/contain behavior), positioning, overlay/dimming treatment, and responsive behavior, so the background looks identical in quality and coverage on both pages and at all breakpoints.
   - **Page structure:** same content container width, padding, vertical rhythm, and header placement as the Notifications page.
   - **Empty state:** when there are no orders, show the same style of empty state used on the Notifications page — same illustration/icon treatment, same typography for the empty title/description, same spacing, and same centered placement.
7.2. Order list items themselves keep their information content, but the page chrome (background, container, spacing, empty state) must be indistinguishable in style from the Notifications page.

**7B. Remove the Reorder page entirely**
7.3. Remove the **Reorder page** from the Storefront completely:
   - The page/route must no longer exist or be reachable.
   - All entry points leading to it (menu items, buttons, links, deep links) must be removed.
   - Any navigation item, tab, or CTA that pointed to Reorder must be removed without leaving gaps, dead links, or broken navigation states.
   - If a reorder *action* is still desired on existing orders, it must live within the Orders page itself (e.g., a per-order action) — as its own standalone page it must not exist.

**Acceptance criteria**
- Orders page background image renders identically to the Notifications page (size, fit, overlay) at desktop and mobile widths.
- Empty Orders state matches the Notifications empty state in illustration, copy style, and layout.
- The Reorder page and every link/route to it are gone; navigating to its old URL produces a proper not-found/redirect — never a broken screen.

## Global Constraints & Notes

- **No coding logic in deliverables:** this prompt defines outcomes, visuals, behavior, and acceptance criteria — implementation approach is left to the executor.
- **Consistency-first rule:** whenever there is a conflict between a local one-off style and the shared design system (admin theme for the Visitor/admin surfaces, storefront theme for the Storefront), the shared design system wins.
- **Direction awareness:** all placement instructions ("before", "in front of") must respect the UI's reading direction (RTL/LTR) at runtime.
- **References:** 📎 `add-to-card.png` (Item 3) and 📎 `order-filter-button.png` (Item 5) are attached — treat them as the visual source of truth for those items.
- **Regression guard:** none of these changes may alter existing business behavior (data, actions, API results) beyond what is explicitly described (Items 6 and 7B being the only functional changes; everything else is presentation/layout).
